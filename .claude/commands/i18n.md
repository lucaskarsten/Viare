# /i18n — Internationalization Audit & Refactor

Audita strings hard-coded em arquivos de UI e migra para `next-intl` (PT/EN).

**Uso:**

- `/i18n` — audita arquivos com mudanças no git diff atual
- `/i18n <caminho>` — audita arquivo ou diretório específico
- `/i18n --new <caminho>` — modo proativo: garantir que arquivo novo já nasça 100% traduzido

## Contexto do projeto

- Locales: `pt` (default) e `en`
- Arquivos de tradução: `messages/pt.json` + `messages/en.json`
- Hook client: `import { useTranslations } from "next-intl"`
- Hook server: `import { getTranslations } from "next-intl/server"`
- Server components async: `const t = await getTranslations("namespace")`
- Client components: `const t = useTranslations("namespace")`
- Interpolação: `t("key", { name: value })` com placeholder `{name}` no JSON
- Raw HTML: `t.raw("key")` + `dangerouslySetInnerHTML` para strings com tags

## Passo 1 — Escopo

Se argumento é path: usar como alvo.
Se `--new`: assumir que o arquivo já foi criado e varrer completamente.
Se nenhum: identificar via `git diff --name-only HEAD` filtrando `.tsx`, `.ts` em `app/`, `components/`, `lib/`.

## Passo 2 — Identificar strings

Catalogar tudo que é **visível ao usuário final** e está em PT/EN hard-coded:

**🔴 Crítico** (migrar sempre):

- Texto dentro de JSX: `<h1>Título</h1>`, `<p>Descrição</p>`, `<button>Ação</button>`
- Atributos visíveis: `placeholder="..."`, `title="..."`, `aria-label="..."`, `alt="..."`
- Strings em state/constants que terminam renderizadas: `const TABS = [{ label: "Todos" }]`
- Template literals com conteúdo UI: `` `${count} aulas` ``

**🟡 Major** (avaliar caso a caso):

- Strings passadas como prop para componente filho que renderiza texto
- Mensagens de erro/toast lançadas de client code
- Valores em useState iniciais que viram texto visível

**🟢 Ignorar:**

- Strings semânticas do domínio (slugs, IDs, enum values: "COMPLETED", "THEORY")
- Textos em arquivos de seed (`prisma/seed.ts`, `prisma/lesson-content.ts`)
- Paths, URLs, tokens CSS
- Chaves internas que não renderizam (data-\* attributes, test IDs)
- Metadata do `<head>` que já vive em `metadata` export

## Passo 3 — Planejar namespace

Para cada arquivo/componente, escolher namespace coerente:

- Match com estrutura existente: `sidebar`, `review`, `lesson`, `goals`, `quiz`, `flashcard`, `courseDetail`, `enroll`, `login`, `search`, `onboarding`, `dashboard`
- Arquivo novo → criar namespace novo se escopo é distinto; reaproveitar se tangente

Convenções de chave:

- `kebab-case` ou `camelCase` consistente dentro do namespace (preferir `camelCase`)
- Prefixos semânticos: `title`, `lede`, `placeholder`, `button`, `empty`, `error`
- Nested para tabs/enums: `tabs.all`, `pace.casual`, `status.completed`

## Passo 4 — Adicionar traduções

Para cada chave nova:

1. Adicionar em `messages/pt.json` com o texto original
2. Adicionar em `messages/en.json` com tradução idiomática (não literal quando não encaixar — traduzir **intenção**)
3. Manter JSON válido (vírgulas, escaping)
4. Alfabetizar chaves dentro do namespace quando ≥ 5 entradas

**Interpolação:**

```json
{ "goalSubtitle": "Você completou {done} de {total} aulas." }
```

```tsx
t("goalSubtitle", { done: 4, total: 6 });
```

**Arrays (para dayLabels, options estáticos):**

```json
{ "days": ["S", "T", "Q", "Q", "S", "S", "D"] }
```

```tsx
const days = t.raw("days") as string[];
```

**HTML embutido (raro):**

```json
{ "hint": "Selecione a aba <strong>Estrutura</strong>." }
```

```tsx
<p dangerouslySetInnerHTML={{ __html: t.raw("hint") }} />
```

## Passo 5 — Refatorar componente

Para **client components** (`"use client"`):

```tsx
"use client";
import { useTranslations } from "next-intl";

export default function Foo() {
  const t = useTranslations("foo");
  return <h1>{t("title")}</h1>;
}
```

Para **server components** (padrão em App Router):

```tsx
import { getTranslations } from "next-intl/server";

export default async function Page() {
  const t = await getTranslations("page");
  return <h1>{t("title")}</h1>;
}
```

Se componente tinha constants com `label`, converter para array de `id` só e resolver label via `t()` no render:

```tsx
// Antes:
const TABS = [{ id: "all", label: "Todos" }, ...];
// Depois:
const TAB_IDS = ["all", ...] as const;
// No render: t(`tabs.${id}`)
```

Se componente tinha função pura que gerava strings (tipo `buildCorpus`), aceitar `t` como parâmetro:

```tsx
type TFn = (key: string, values?: Record<string, string | number>) => string;
function buildCorpus(data: Data[], t: TFn) { ... }
```

## Passo 6 — Verificar

```bash
npx tsc --noEmit
npm run lint
```

Checar que:

- JSON de ambos locales tem as mesmas chaves (shape idêntico)
- Nenhum `t("key.que.nao.existe")`
- Placeholder em JSON bate com `values` passados no componente

## Modo proativo (--new)

Quando invocado com `--new` (ou detectado automaticamente em novo arquivo UI):

1. **Antes** de escrever o código: já listar strings previstas e sugerir chaves.
2. Propor trechos prontos com `t()` em vez de hard-code.
3. Alertar se há string nova cujo namespace melhor encaixe é um já existente — reutilizar se semântica bater.

## Anti-padrões a evitar

- ❌ Concatenar strings traduzidas: `` `${t("hello")} ${name}` `` → use interpolação: `t("hello", { name })`
- ❌ Traduções condicionais com ternário: `count === 1 ? "aula" : "aulas"` → criar `lessonUnit` / `lessonsUnit` separadas
- ❌ Traduzir dado de domínio (títulos de curso, descrições vindas do DB) — isso é conteúdo, não UI
- ❌ Copiar texto PT para en.json e deixar para depois — traduzir já no momento

## Checklist pré-commit

Ao finalizar qualquer feature/fix que toque `.tsx`:

- [ ] Todas as strings novas em PT/EN?
- [ ] JSON válido em ambos locales?
- [ ] TypeScript compila?
- [ ] Namespace coerente com estrutura existente?
- [ ] Interpolações consistentes (mesmas placeholders em ambos locales)?
